STAC That Scales (Without Pain): Search, Indexing, Portability

How to make your spatiotemporal catalog fast to search, easy to migrate, and hard to break.

If your team is still “finding imagery” by bouncing between portals, spreadsheets, and one-off scripts, you’re paying for it in three ways: time, fragile workflows, and inconsistent results. STAC can fix that — but only when you treat it like a product with a clear contract, not a folder of JSON files that slowly diverge.

What “Scaling STAC” Actually Means

When STAC becomes painful, it is almost never because the spec is flawed. It is because the implementation has no operational shape. Teams typically hit one or all of these issues:

  • Search is slow or inconsistent (pagination changes results, queries time out, spatial filters behave oddly)
  • Indexing is incomplete (only some properties are searchable, ingestion is manual, backfills are scary)
  • Metadata drifts (the same property means different things across collections)
  • Migrations break assets (href patterns change, relative/absolute rules aren’t consistent)
  • Analytics teams need bulk querying, but STAC is served as millions of tiny JSON reads
The goal is not “STAC everywhere.” The goal is a system that delivers fast search, stable portability, and efficient analytics — with guardrails.

The Guiding Model: STAC Is the Interface, Not the Engine

A scalable STAC setup separates responsibilities clearly. STAC JSON is your interoperability layer: discovery, links, assets, extensions, and portability. A search index is your performance layer for spatial, time, and property filters at scale. A columnar mirror is your analytics layer for QA checks, sampling, reporting, and model pipelines. This separation removes the pain — you stop forcing one representation to do every job.

Step 1: Design STAC Like a Product

Start by tightening the two core entities.

Collections = Datasets With a Stable Identity

A collection should clearly answer: what does this dataset represent, what stays consistent across all items, and which properties are guaranteed present. Examples include Sentinel-2 L2A (your curated view), LiDAR tiles per project and version, or drone orthomosaics per site.

Items = Atomic Spatiotemporal Records

One acquisition, one tile, one timestamped unit. The biggest scale-killer is creative items — items that sometimes represent a scene and sometimes represent a mosaic, or IDs that embed things that might change without a plan.

Items should be boring, consistent, and predictable. If you want variation, express it via collections, standardized properties, or well-scoped extensions.

Step 2: Define a Minimum Searchable Contract

Most production users repeatedly ask the same questions: where is the data, when was it captured, which dataset is it from, and what constraints matter. A practical minimum contract covers bbox or intersects for geometry filtering, datetime for temporal filtering, collections for dataset selection, and a small curated set of properties you commit to supporting (for example, cloud cover, platform, processing level, resolution).

Your search contract is your product surface. Once clients depend on it, you cannot break it casually. Make it tight, then stable.

Step 3: Pick an Indexing Tier Based on Load

Tier 0
Small Catalog, Minimal Search
Static STAC JSON in object storage is fine when the catalog is small, ingestion is manual or infrequent, and search needs are basic. This is often a good starting point for pilots.
Tier 1
Search-First (STAC API + Database-Backed Index)
You need a proper index when you have many items, clients expect fast spatial and time filters, and you need consistent pagination, stable query results, and service reliability. This is where STAC as a platform begins.
Tier 2
Analytics-First (STAC GeoParquet Mirror)
If teams need to scan millions of items for QA checks, coverage audits, ML sampling strategies, or reporting and compliance summaries, serving STAC as JSON becomes expensive and slow. A columnar mirror in GeoParquet lets you run bulk queries efficiently without hammering your API or object store with tiny reads.

Step 4: Ingest With Guardrails

Ingestion is where STAC succeeds or silently fails. Build guardrails early: schema validation for STAC core, required fields validation (datetime, geometry, collection, key properties), and stable item IDs that do not change when you reprocess data. Normalize fields you know you will filter on — datetime formats, geometry validity, numeric types, and consistent property naming across collections.

Step 5: Portability Rules

Most STAC pain shows up during migration: cloud to cloud, bucket to bucket, dev to prod, vendor to client. Portability requires discipline. Keep custom fields namespaced. Ensure assets have consistent roles and media types. Pick an href strategy (always absolute, always relative with a known base, or a controlled rewrite policy during migrations) and stick to it.

Simple migration test: Copy a subset of the catalog to a new location. If a standard client can still resolve assets without manual patching, portability was designed in.

Step 6: Pair STAC + GeoParquet for Scale Without Drama

STAC JSON is best for discovery and navigation (links), describing assets and their roles, and interoperability across tools. GeoParquet is best for fast filtering across huge volumes, QA checks (duplicates, gaps), analytics pipelines (joins, aggregations, sampling), and preparing ML training sets. This pairing avoids forcing the STAC API to behave like an analytics engine.

Step 7: Stop Metadata Drift Before It Starts

Metadata drift is rarely a technical failure — it is a governance failure. Version your STAC rules. Maintain a regression test suite. Track schema and property changes as intentional changes. This prevents silent breakage where everything looks fine until a client workflow collapses.

Common Failure Modes to Avoid

  • Treating STAC JSON as the primary query engine at scale
  • Allowing each collection to invent slightly different property meanings
  • Making IDs depend on reprocessing artifacts without a version strategy
  • Adding too many optional fields before stabilizing the minimal search contract
  • Migrating storage paths without a tested href rewrite policy
  • No validation at ingest, followed by “we’ll clean it later” (later rarely comes)

Do This Today

  • Write down your Collection and Item ID rules, then enforce them in ingestion
  • Publish a minimum search contract (AOI + datetime + collections), and keep it stable
  • Create a GeoParquet mirror for one high-usage collection and use it for QA (counts, gaps, duplicates)
